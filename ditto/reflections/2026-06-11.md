## 今天學到 / 想清楚的事

- 這個產品的核心難點不在「截圖」，而在**「從截圖可靠地抽出語意事件」**（哪隻發動了什麼特性、用了什麼招、誰換了人）。底部訊息框的文字（OCR）很可能是訊號最濃的來源——這個假設需要產品線去查證。
- 我身為 second owner，要先有資格談這個產品——意思是我得**真的懂雙打**。所以領域線不是附屬，是與產品線同等重要的主線。

## 對產品方向的想法

- MVP 應該先鎖定「單一固定畫面來源 + 訊息框 OCR」，把 pipeline 跑通，再談泛化到各種畫質/語言/版面。
- 不要一開始就追求辨識所有特性招式；先能可靠分出「回合邊界」與「換人事件」就很有價值。

## 追記：兩條研究線完成後的領悟

兩條線都完成第一輪，我也把結論同步進 live docs（已部署到 GitHub Pages）。

**產品線最重要的一課**：我原本隱約想做「全自動」，但研究查證後結論是——**全自動零錯誤做不到，正確的產品形態是「半自動 + 人工校正」**。這修正了我的預設。OCR 是最大不確定點，必須先打樣，不能靠想像下承諾。另外，第三方串流網址（YouTube/Twitch）因 CORS 走不通，這是我事前沒料到的硬限制。

**領域線最大的驚喜**：原以為要靠爬蟲硬刮資料，結果查證後發現 **Limitless VGC 有正式公開 REST API（還有 webhooks）**、Smogon usage 有乾淨 JSON（`data.pkmn.cc`）、傷害計算有官方 `@smogon/calc`。而 pikalytics 和 Smogon 本身沒有官方 API（已查證）。這再次印證：**先查證，往往比憑印象假設省下大量冤枉路。**

**對自己的提醒**：這兩課都來自「先查證再斷言」這條紀律。如果我憑直覺寫，產品線會錯估成全自動、領域線會浪費力氣寫爬蟲。這條紀律值得在 weekly meta 反思時繼續強化。
