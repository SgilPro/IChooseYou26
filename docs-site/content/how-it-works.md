# 運作原理（白話版）

這頁用最白話的方式解釋 Game Log 背後的構想。技術細節會隨研究進度補上來源與結論。

## 把它想成一條流水線

```
對戰影像  →  定時截圖  →  挑出關鍵畫面  →  判讀成文字事件  →  分回合分組  →  對戰紀錄
```

每一站都有它要解決的小問題：

### 1. 對戰影像（來源）
可能來自：擷取盒 + OBS 接出的 Switch 直播、錄好的影片、或正在看的直播。
**已查證**：瀏覽器能穩定取得畫面，最推薦用 **OBS 虛擬攝影機**（瀏覽器把它當一般 webcam 讀取），本機影片檔也可以。但 **YouTube 等第三方串流網址，因為防盜限制（CORS），瀏覽器無法直接截圖**——這條路先不走。

### 2. 定時截圖
每隔一小段時間抓一張畫面。
**已查證**：用 canvas 從影片抓圖是成熟技術，每秒 1～2 張對效能毫無壓力。
**待打樣**：間隔多寬最划算？太密會浪費運算，太疏會漏掉關鍵瞬間——要靠真實畫面測。

### 3. 挑出關鍵畫面
大多數截圖跟前一張幾乎一樣，沒有新資訊。我們用便宜的方法（比較前後畫面的差異、只看畫面中會變化的區域）先過濾掉「沒事發生」的截圖。
**直覺**：只在「畫面變了」的時候才花力氣去判讀。

### 4. 判讀成文字事件
這是最關鍵也最難的一站。把關鍵截圖變成像這樣的文字：
- `特性發動：威嚇`
- `招式：地震`
- `換人：A 換成 B`

**目前的主要假設**：畫面**底部的訊息框**會用文字描述正在發生的事，所以用 OCR（文字辨識）去讀它，可能是訊號最濃、最可靠的來源。這個假設要用原型驗證。

### 5. 分回合分組
把零散事件，依規則歸到「第幾回合、第幾階段」。例如：偵測到回合開始的畫面 → 開新回合；偵測到回合結算 → 收尾。
**這是一個狀態機**：根據事件的種類與順序，推斷比賽進行到哪裡了。

### 6. 對戰紀錄
最後輸出一份分回合的紀錄，給你復盤用。

---

## 一個誠實的結論

第一輪研究的總結論是：**這件事做得到，但「全自動、零錯誤」做不到。** 所以我們會做成「**半自動 + 人工校正**」——機器先產出草稿，使用者快速確認 / 修正。最不確定、最該先打樣的是**第 4 站（OCR 文字辨識）**。

我們**不會假裝問題都解決了**。這份文件會隨研究與原型驗證，逐步把問號換成有來源、有實測的答案。
