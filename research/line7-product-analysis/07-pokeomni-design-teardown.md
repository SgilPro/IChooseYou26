# PokéOmni 設計拆解：設計元素、風格，以及推估的做法

> 2026-11-14。屬於 UI/UX 線。`04-ux-audit-pokeomni.md` 談的是「好不好用」，這份談的是「它長什麼樣、怎麼做出來的」。
> 方法：用瀏覽器開首頁與「關於」頁，讀頁面實際載入的樣式表、字型、圖片、動畫與腳本檔名，並量幾個元件的實際樣式值。
> **凡是寫「推估」的都是從這些線索推論的，不是對方公開說明的**。它的原始碼沒有公開，我也沒有反編譯它的程式。我們只分析做法，不複製它的程式碼或素材。

## 一句話總結

PokéOmni 是「**掌機圖鑑機的外殼，包著一個現代的資料工具**」：米白紙色底、深色 2px 粗框、不模糊的硬邊陰影、像素字與像素小圖，配上圖鑑紅、行動綠兩個主色。技術上是很常見的現代前端組合（React、Tailwind、Vite、Firebase、Cloudflare），特別的是它的**設計代幣分了兩層**，而且**所有動畫都是純 CSS**，沒有用畫布或影片。

## 一、視覺語言

### 1. 色彩

它的顏色分兩層命名。第一層是「顏料」（`arcade-*`），第二層是「用途」（`color-*`），元件只用第二層。

**基礎色（顏料層）**

| 名稱 | 色碼 | 用在哪 |
|---|---|---|
| paper 紙白 | `#FAFBF3` | 整站底色、卡片底 |
| ink 墨黑 | `#2A2A2A` | 文字、所有粗框 |
| ink-soft 棕灰 | `#5B4A3A` | 次要文字、陰影顏色 |
| pokedex-red 圖鑑紅 | `#A83838` | 導覽重點、表頭、圖鑑機外殼 |
| 行動綠 | `#3AAC4F` | 主要按鈕、「我方」 |
| sapphire 藍 | `#3A5FCD` | 特殊招式、抵抗、防禦 |
| mega 紫 | `#8B5CF6`（深 `#6D28D9`） | Mega 進化相關 |
| gold 金 | `#D4A843` | 點綴 |
| highlight 奶黃 | `#FFF7D6` | 卡片內側的亮邊 |
| parchment 羊皮紙 | `#F5E9D0`、`#EAD8B3` | 區塊底、骨架載入色 |

**用途色（語意層）**：名稱直接對應對戰概念，這是它做得最講究的地方。

| 類別 | 代幣 |
|---|---|
| 陣營 | `side-mine`（綠）、`side-opp`（紅 `#C73A3A`） |
| 對位優劣 | `matchup-adv`（綠 `#23833A`）、`matchup-dis`（紅）、`matchup-even`（棕） |
| 傷害升降 | `dmg-up`（紅）、`dmg-down`（藍） |
| 屬性效果 | `eff-super`、`eff-resist`、`eff-immune`（灰 `#899198`） |
| 招式分類 | `move-physical`（紅）、`move-special`（藍）、`move-status`（棕） |
| 角色 | `role-attack`、`role-defense` |
| 其他 | `usage`（使用率，綠）、`mega`、`speed-2`、`speed-3`、`priority-up`、`priority-down` |

透明度也取了名字：`/faint`、`/muted`、`/soft`、`/emphasized`，而不是寫數字。

整體只有紅、綠、藍三個有彩度的功能色，其餘都是紙色與棕灰。這是它「東西很多卻不雜」的主要原因。

### 2. 字型

| 用途 | 字型 | 來源 |
|---|---|---|
| 內文 | Plus Jakarta Sans（英數）加系統中文字（蘋方、思源黑體、微軟正黑） | 自己的主機 |
| 像素標題（英數） | Press Start 2P | 自己的主機 |
| 像素標題（中文） | Cubic 11（俐方體 11 號） | jsDelivr 上的開源字型庫 |

- 像素字的堆疊是 `"Press Start 2P", "Cubic 11", 蘋方…`，英文走 Press Start 2P，中文落到 Cubic 11。站名「PokéOmni」和圖鑑卡片上的寶可夢名字都用這組。
- 字級只有少數幾階：內文 16、次要 14、標籤 12、標題 36 與 48；像素字另有 10、12、14、18 四階。
- 中文像素字只載入需要的字碼範圍（CJK 區段），不會拖慢英文頁面。

### 3. 形狀、邊框與陰影

- **邊框**：幾乎所有元件都是 2px 實線墨黑框。
- **圓角**：只有兩種，卡片 12px、按鈕與標籤是全圓角膠囊。
- **陰影全部是硬邊、不模糊**，像貼紙往右下錯位。它定義了一整組：

| 名稱 | 值 | 用在哪 |
|---|---|---|
| sticker | `3px 3px 0 #7B6D5F` | 按鈕 |
| sticker-sm、xs、lg | 2px、1px、5px 的同款 | 小按鈕、標籤、大元件 |
| card | `4px 4px 0 #5B4A3A` 加 `inset 0 0 0 2px #FFF7D6` | 卡片：外面硬陰影，裡面一圈奶黃亮邊 |
| card-sm、lg、mirror | 2px、6px、往左下的版本 | 不同大小與左右對稱的卡片 |
| inset | 四邊向內的淡線 | 輸入框的凹陷感 |
| cockpit 系列 | 上亮下暗的內陰影 | 圖鑑機外殼上的按鈕、鏡頭、螢幕 |
| soft | `0 4px 16px` 淡陰影 | 少數浮層（唯一有模糊的） |

卡片「外硬陰影加內亮邊」這個組合，是整站質感的來源：2px 黑框、框內一圈奶黃、框外一塊棕色錯位。

### 4. 圖像

- **寶可夢圖**是 96×96 的像素小圖，檔名用圖鑑編號與型態編號（例如 `/sprites/pokemon/727.png`、`10061.png`），另有背面圖（`/sprites/pokemon/back/`）。這和 PokeAPI 的 sprites 編號方式一致，「關於」頁也寫明來源是 PokeAPI。
- 圖放在自己的主機上，不是連到 PokeAPI。
- 小圖放大到 2 倍以上顯示（首頁戰鬥場景裡放大到約 210 到 250px），靠 `image-rendering: pixelated` 保持像素銳利，再加一層不模糊的投影。
- 屬性圖示、道具圖、精靈球圖各有自己的資料夾（`/sprites/types/`、`/sprites/items/`、`/sprites/balls/`）。「關於」頁寫這些整理自 pokesprite、Pokémon Showdown 與 Bulbagarden Archives。
- **頁首 logo 是一顆會動的精靈球**：每次載入隨機換一種球（我看到過超級球、紀念球等），有一個晃動後打開的動畫，滑鼠移上去會暫停並放大。

### 5. 游標

- 整站換成像素風的自訂游標，分一般、可點、不可點、說明、輸入、抓取六種，每種還有「按下」的版本。
- 做法是把小圖轉成 base64 直接寫在樣式表的變數裡，不用另外下載。
- 「關於」頁寫游標來自 Kenney 的像素游標包（CC0 授權）。

### 6. 動態

樣式表裡共有 55 組動畫，全部是 CSS，頁面上沒有畫布也沒有影片。

| 類別 | 例子 | 做法 |
|---|---|---|
| 一般互動 | 按鈕、連結 | 150 毫秒淡入，滑鼠移上去時改成 75 毫秒（進快出慢） |
| 進場 | 換頁、卡片、下拉、抽屜、底部面板 | 往上位移 8 到 22px 加淡入 |
| 精靈球 | 投擲、晃動捕捉、打開、三顆星 | 旋轉與縮放的關鍵影格 |
| 對位 | 左右滑入、撞擊、矩陣格子逐一出現 | 位移加延遲 |
| 首頁戰鬥場景（`lp` 開頭） | 雲飄、我方出招、對方受擊、收回、派出 | 見下一節 |
| 首頁功能示範（`fs` 開頭） | 選寶可夢、能力條長出來、血條、傷害數字、切分頁 | 12 秒或 20 秒無限循環的時間軸 |

它有處理「減少動態效果」的系統設定，也用媒體查詢區分滑鼠與觸控裝置。

## 二、首頁是怎麼做的（推估）

首頁那個「戰鬥畫面」看起來像遊戲，其實是一般的網頁元素疊出來的：

1. **背景**是一條直向漸層，從天空藍到草地綠。天空與草地的交界用兩個很近的色標（30% 與 32%）做出一條硬邊地平線，不是圖片。
2. **雲**是 SVG，各自用 46 秒與 60 秒的週期左右飄。
3. **寶可夢**是前面說的像素小圖放大。對方用正面圖放右上，我方用背面圖放左下，這是寶可夢遊戲的標準戰鬥視角。腳下的影子是一個放射狀漸層的橢圓。
4. **動作**靠幾組關鍵影格輪流觸發：我方往右上衝一下再回來（出招）、對方左右抖動並瞬間變亮（受擊）、縮小消失（收回）、帶一點回彈地冒出來（派出）。
5. **兩側的六格隊伍列**用小圖加彈出動畫，被選到的那隻加亮框。
6. 往下的「功能示範」區塊，是用同一套手法做的**假介面循環動畫**：畫面上的圖鑑卡片、能力條、傷害數字都是真的網頁元素，照固定時間軸自己播放，不是錄影。

這種做法的好處是檔案很小、文字清晰、可以跟著語言切換，壞處是時間軸要手工調，改一個地方常要連動改好幾組影格。

## 三、技術組成（推估）

| 項目 | 推估 | 依據 | 把握 |
|---|---|---|---|
| 前端框架 | React | 根節點是 `#root`，上面有 React 的內部標記；有 `vendor-react` 檔 | 高 |
| 打包工具 | Vite | 檔名帶雜湊（`index-BzMP1-v2.js`）、用 `modulepreload`、依頁面拆檔（`LandingPage-…js`） | 高 |
| 樣式 | Tailwind CSS 第 3 版，加自訂主題 | 樣式表裡有 Tailwind 第 3 版特有的 `--tw-*` 預設變數；class 是 `bg-color-surface`、`rounded-arcade-pill`、`shadow-sticker` 這類自訂名稱 | 高 |
| 登入與雲端隊伍 | Firebase（登入，可能加資料庫） | 有 `vendor-firebase` 檔；頁首有 Google 登入；首頁文案寫隊伍「已同步雲端」 | 中高 |
| 防濫用 | reCAPTCHA Enterprise，推估接在 Firebase App Check | 載入了 `recaptcha/enterprise.js`；「關於」頁寫「本站受 reCAPTCHA 保護」 | 中 |
| 主機與流量統計 | Cloudflare | 載入 Cloudflare 的流量統計腳本，路徑有 `cdn-cgi` | 高（是否用 Cloudflare Pages 不確定） |
| 可安裝成 App | 有 manifest 與 iOS 相關設定 | 有 `manifest.json`、`apple-mobile-web-app-capable`、針對獨立視窗模式的樣式 | 高；我查的當下沒有註冊離線快取 |
| 資料 | 大多在建置時打包成靜態檔 | 有 `move-data`、`ability-data`、`item-data`、`pokemon-movesets`、`usageCache`、`usageTeams`、`damageCalc` 等獨立的程式檔 | 中高 |
| 搜尋引擎 | 首頁內嵌結構化資料（JSON-LD）、完整的社群分享標籤 | 頁面原始碼 | 高 |

幾個從檔名看得出來的工程習慣：
- React 與 Firebase 各自拆成獨立檔，改版時使用者不用重新下載。
- 圖示、屬性標籤、招式列這些小元件各自成檔，首頁只預先載入會用到的。
- `<html>` 上有 `data-cursor="v6"`，游標換過至少六版；手機選單裡看到版本號 v1.10.1 和更新紀錄。這個站迭代得很勤。

## 五、推估它的製作方式

以下推論程度較高，請當成參考：

- **先定了一套「掌機圖鑑」的隱喻，再往下推出所有細節**。紅色外殼、圓燈、十字鍵、像素字、像素游標、精靈球 logo 都服務同一個主題。這種一致性通常來自一開始就寫下的設計規則，而不是邊做邊加。
- **代幣先行**。陰影有 20 種具名樣式、顏色有約 65 個具名代幣、透明度有名字，元件裡幾乎看不到寫死的數值。這表示它有一份集中管理的主題設定檔，改一個顏色全站會跟著變。
- **規模像個人或很小的團隊**：聯絡方式是單一信箱，素材全部來自開源或社群資源，沒有自製插畫。美術上的份量是靠「現成像素圖加一套嚴格的框線與陰影規則」堆出來的，不是靠畫。
- **花最多工的地方應該是首頁的兩段循環動畫和語意色彩系統**，這兩樣都沒有現成的東西可以套。

## 六、對我們有用的地方

**值得學的**
1. **代幣分兩層**：顏料層與用途層分開，而且用途層直接用領域語言命名（我方、對方、優勢、劣勢、物理、特殊）。我們的 `tokens.css` 目前只有一層，戰術定位標籤的黃藍綠是寫死在頁面裡的，可以照這個方式收進代幣。
2. **用很少的規則做出辨識度**：一種框線粗細、兩種圓角、一個陰影家族。我們現在的圓角有 6、7、8、9、10、12、14 好幾種。
3. **像素小圖放大加 `pixelated`**：96px 的圖就夠用，不需要大圖，載入快。
4. **「關於」頁的寫法**：逐項列來源、授權、資料更新日期，加上權利人的聯絡管道。這正是 `05-compliance.md` 指出我們缺的東西，可以直接參考它的結構。
5. **純 CSS 的假介面示範**：之後我們要在首頁展示功能時，這比放截圖或影片輕，也能跟著語言切換。

**不建議學的**
1. 像素中文字用在需要快速辨認的地方（寶可夢名字），易讀性比一般黑體差。
2. 裝飾性的假按鈕（十字鍵、A／B 鈕、圓燈）。
3. 55 組動畫的維護成本。我們是靜態頁加少量腳本，沒有必要走到這個量。
4. 整站換游標。有特色，但對使用工具沒有幫助，還要維護「按下」的版本。

## 限制

- 只看了首頁與「關於」頁的樣式與資源清單，加上先前審查時看過的幾個工具頁畫面。
- 技術組成是從檔名、標記與載入的資源推論的；後端怎麼存資料、有沒有伺服器端程式，從外面看不到。
- 色碼取自樣式表裡的值，我只把常用的列出來，沒有列完全部約 65 個。
- 「製作方式」那一節是推論，沒有任何來自作者的說明可以佐證。
