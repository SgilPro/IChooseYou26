# 00 — 執行摘要（給非技術讀者）

> 這份文件用白話說明：我們想做的「Game Log（對戰紀錄／復盤）」工具在技術上**做不做得到**、**哪裡會卡**、以及**建議怎麼分階段做**。完整技術細節分散在 01～07 各檔。

## 一句話結論

**做得到，但「全自動、零錯誤」做不到。** 建議走「**半自動 + 人工校正**」路線：機器先抓出關鍵畫面、辨識出大部分文字事件，使用者再快速確認／修正。這在技術上風險最低、最快能做出可用的 MVP。

## 我們要做的事，拆成五個步驟

1. **拿到畫面**（影像來源）：使用者把 Switch 的對戰畫面餵進網頁。
2. **定時截圖**（抓影格）：每隔一段時間（例如每秒 1 張）擷取一張畫面。
3. **過濾出「有用的」截圖**（關鍵影格過濾）：丟掉沒變化的畫面，只留下「有事情發生」的那幾張（換寶可夢、出招、特性發動…）。
4. **把截圖變成文字**（辨識 / OCR）：讀畫面下方的訊息框文字（例如「胡帕的特性威嚇發動了！」），這是最可靠的資訊來源。
5. **整理成一回合一回合的紀錄**（結構化）：把零散事件依「第幾回合、誰先動」歸位，產出乾淨的復盤紀錄。

## 每一步的可行性（紅綠燈）

| 步驟 | 可行性 | 重點說明 |
|---|---|---|
| 1. 拿到畫面 | 🟢 綠 | 瀏覽器原生支援。**最推薦用 OBS 虛擬攝影機**（瀏覽器當成一般 webcam 讀取），其次是螢幕分享（getDisplayMedia）。本機影片檔也可以。**YouTube 等第三方串流網址因為防盜限制（CORS），瀏覽器無法直接截圖**，是個雷。 |
| 2. 定時截圖 | 🟢 綠 | 用 canvas 從影片畫面抓圖是成熟技術，每秒 1～2 張對效能毫無壓力。 |
| 3. 過濾關鍵影格 | 🟢 綠（規則）/ 🟡 黃（調參） | 用「感知雜湊（perceptual hash）」比對前後畫面差異很便宜也很快。難的是**定義「什麼叫關鍵變化」的規則**，需要靠真實對戰畫面反覆測試調整。 |
| 4. 辨識文字 | 🟡 黃 | **這是整個專案最不確定、最需要打樣的環節。** 純瀏覽器端 OCR（Tesseract.js）對日文/中文遊戲字體準確度有疑慮；雲端 OCR（Google Vision）準很多但要錢、要後端。寶可夢/招式/特性建議**比對固定字典**而非純辨識。 |
| 5. 結構化 | 🟢 綠 | 寶可夢對戰有固定流程（出招順序看速度、回合結束結算），可用「狀態機」規則歸位。邏輯複雜但確定性高。 |

## 最大的三個風險（要先打樣驗證）

1. **OCR 準確度（最高風險）**：遊戲畫面文字辨識到底準不準，沒實測過誰都不敢保證。**第一個該做的原型就是拿幾十張真實對戰截圖測 OCR。**
2. **影像來源穩定性**：OBS 虛擬攝影機在不同 OS／瀏覽器的相容性、解析度，需要實測。第三方串流網址基本上走不通。
3. **規則覆蓋率**：寶可夢的特性、招式、狀態變化非常多，規則要能涵蓋常見情境，需要大量真實樣本。

## 建議的技術方向（MVP）

- **MVP 走「客戶端為主 + 輕後端」**：影像處理（截圖、過濾）全在瀏覽器做；OCR 在 MVP 先用 Tesseract.js 試水溫，若準確度不足再把畫面送到後端／雲端 OCR。
- **輸入只支援兩種**：OBS 虛擬攝影機（即時）＋ 本機影片檔（事後）。**先不做第三方串流網址。**
- **輸出是「可編輯的時間軸事件清單」**：機器產草稿，使用者校正。**不追求全自動。**
- 技術棧建議：React + TypeScript 前端、Web Worker 跑運算、IndexedDB 暫存影格、選配一個 Node/Serverless 後端做雲端 OCR 代理。

## 分階段範圍

- **MVP**：本機影片檔 → 定時截圖 → 關鍵影格過濾 → OCR 訊息框 → 產出可編輯事件清單（含截圖縮圖）。先驗證辨識準確度與規則。
- **v1**：加 OBS 虛擬攝影機即時擷取；加寶可夢/招式/特性字典比對；自動分回合。
- **v2**：HP 條／狀態圖示視覺辨識、雲端 OCR、帳號雲端儲存、多語系、分享復盤連結。

## 接下來建議

先做兩個小原型（各約數天）：
1. **OCR 原型**：50～100 張真實對戰截圖，比較 Tesseract.js vs Google Vision 在訊息框文字上的準確度。
2. **擷取原型**：OBS 虛擬攝影機 → 瀏覽器 getUserMedia → canvas 截圖 → 感知雜湊過濾，跑一場真實對戰看留下多少張、漏了沒。

兩個原型結果出來，才能對「全流程到底多準、多快」給出有把握的承諾。
